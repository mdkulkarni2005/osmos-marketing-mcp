# Deduplication

Run after all dimension documents have emitted scenarios, before
prioritization's output is finalized in the matrix.

## What counts as a duplicate

Two scenarios are duplicates if they would exercise the **same request shape
against the same endpoint and assert the same expected result**, even if
they were generated by different dimension documents. This commonly happens
because dimensions overlap by design (e.g. a required enum field is touched
by both [[negative-testing]] "missing required field" and [[enum-testing]]
"missing value if required").

## What counts as equivalent (collapse into one)

- Two boundary cases that resolve to the identical concrete value (e.g.
  `minimum=1` and a separately-generated "smallest valid value" case both
  producing `daily_budget_multiplier: 1`).
- A generic "invalid type" case and a format case that both send the same
  malformed value for the same field.
- Redundant combinations in dependency testing: if `IF budget_type=LIFETIME_BUDGET THEN daily_budget forbidden`
  and a separate "wrong type for daily_budget" case both use a request
  where `daily_budget` is absent — keep the one that targets the
  documented rule (dependency), drop the redundant type-mismatch framing
  since the field isn't even applicable in that state.

## What to keep even if similar (distinct risk, don't collapse)

- Same field, same "invalid" framing, but different failure mode (e.g.
  `max_limit: "abc"` for wrong-type vs `max_limit: null` for null-testing) —
  these exercise different validation code paths and stay separate.
- The same boundary value reached via two different *documented* rules (e.g.
  a value that is simultaneously the numeric maximum and also forbidden by a
  conditional rule) — keep both, but note the overlap in `risk` so a human
  reviewer understands why two scenarios look similar.

## Merge procedure

1. Group scenarios by `(endpoint, method, normalized_request_diff_from_baseline, expected_result)`.
2. Within a group, keep the scenario whose `category`/`subcategory` most
   precisely names the risk (prefer the more specific dimension over a
   generic one).
3. Record the dropped scenario_ids in a short "deduplicated" note attached to
   the surviving scenario's `risk` field only if it aids traceability;
   otherwise just drop silently — dedup is expected, not a defect.
4. Re-run the coverage calculation in [[coverage-model]] only after dedup, so
   coverage reflects the final, deduplicated matrix.
